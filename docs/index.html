Your agent
runs as you.

Which means every API key on the machine is one command away from it — cat .env, printenv, a glance at your shell history. Coding agents read files and run commands; that's the entire job.

shush lets an agent call the API without ever holding the credential. It asks a localhost proxy, the proxy injects your key upstream, and the agent gets the response back — never the key.

01

How keys leak to agents

None of these are exotic attacks. They're the ordinary behaviour of a tool you deliberately gave filesystem and shell access to — and every one of them ends with your key in a context you don't control.

cat .env

Files in the repo

Reading your project is the agent's core loop. A key in .env, a config file, or a stray notes file is simply part of the codebase to it.

printenv | grep KEY

Inherited environment

Export a key into your shell and every process the agent spawns inherits it. One command dumps the lot.

~/.bash_history

Shell history

A key pasted inline once lives in history forever, and history is a file like any other.

> transcript.log

Transcripts and logs

Agents echo commands, capture output, and paste it into issues, pull requests, and chat — sometimes to a provider you didn't pick.

mcp.json

Tool and MCP config

Keys pasted into tool configuration are plain JSON sitting in a path the agent can read on request.

gopass show api_key

Your password manager

Most secret tools are built to decrypt and print. Once the agent is cached, an agent with shell access can read the whole store — no attack required.

02

Four levels of not leaking

Each level is independent and opt-in. They differ in one specific way: how much of your key the agent ever touches.

01

Vaultshush set · shush run

No .env to read, nothing in shell history, nothing inherited by unrelated processes. The agent still holds the key — it's in the environment of the process you launched, so this closes the files but not the process.

02

Protected secretsshush enroll · shush protect

Encrypted at rest under a key only your unlock factor recovers. An agent that goes rummaging in Credential Manager finds ciphertext, and unlocking needs a passphrase, a gesture, or a physical touch it can't perform.

03

Proxy modestart hereshush proxy start

The agent never receives the key. It calls 127.0.0.1 by provider name; the proxy injects your credential into the outbound HTTPS request and strips whatever the client sent. The agent gets the API's answer and nothing else.

04

Service modeinstall_proxy_service.ps1

The vault moves to a Windows account you cannot read from your own session. No agent running as you can retrieve a value, because there is no read operation to call. Create, list and delete keep working through a write-only pipe.

Levels 2–4 rely on unlocking the vault yourself. Four factors do that, and any enrolled one opens it — so enroll two and a lost key isn't a lost vault.

⌨️

Passphrase

PBKDF2-SHA256, 600k iterations. Works anywhere, nothing to carry.

👤

Windows Hello

PIN, fingerprint or face. TPM-bound, so a copied vault is inert elsewhere.

🔑

FIDO2 key

A YubiKey touch. The secret never leaves the token — and an agent has no fingers.

💾

Keyfile

A thumbdrive. Plug in to work, unplug to shut the vault. No typing at all.

On gopass — the closest sibling

Local, offline, free, no account, and with far better-scrutinised cryptography than this project has.

But its model is decrypt-and-print, and once gpg-agent has cached your passphrase it stops prompting. An agent doesn't need to defeat anything — it just runs the command. That gap is structural, not a bug.

Use 1Password or Doppler if…

More than one person needs the key. Sharing, rotation and audit trails all beat what's here.

Use gopass or envy if…

You're not on Windows. shush is Windows-only by design and will stay that way.

Use anything older if…

You need audited cryptography. This implements its own AES-CBC+HMAC, PBKDF2 and CTAP2 stack — careful and test-covered, but new and unaudited.

05

What it doesn't do

▲ Read this before trusting it with anything

  • run --env still hands the agent your key. It's in the child's environment by design, so a tool that prints its own environment prints the key. Use proxy mode when the agent is the thing you're worried about.
  • It can't protect an unlocked session. Once a key is unlocked and in a process, the plaintext is in memory. Nothing here changes that.
  • A keyfile is a bearer token. Anyone — or anything — that copies it holds the vault, and copying leaves no trace. Only the FIDO2 factor resists that.
  • TOTP is deliberately not offered. An authenticator app verifies, it doesn't encrypt, and verifying needs the seed stored on the same machine as the keys it guards.
  • Hello and FIDO2 aren't hardware-verified yet. Passphrase and keyfile are covered by automated tests on both PowerShell hosts; the other two are implemented and test-covered in software but haven't met a real TPM or token. Don't make either your only factor until you've run the hardware suite.
  • It is not a defence against a hostile administrator on the machine, and never claimed to be.
